**Decisions / gotchas:**
- **Postgres port conflict**: a native Postgres.app instance on this Mac was already bound to host port 5432 (`launchctl list | grep postgres` showed `com.postgresapp.Postgres2LoginHelper`), silently shadowing the Docker container's `5432:5432` port mapping — `docker compose ps` showed the container healthy, but `psql`/`alembic` connecting to `localhost:5432` were actually hitting Postgres.app and getting `password authentication failed`. Fixed by remapping the compose file to `${POSTGRES_PORT:-5433}:5432` and updating `.env`/`.env.example`/`config.py`'s default accordingly. Container-to-container traffic (api → `postgres:5432` inside the Docker network) is unaffected — only the host-side port changed. If a future session hits `password authentication failed` against a container that `docker compose ps` shows as healthy, check for a competing local Postgres install before assuming the credentials are wrong.
- **Timezone-naive vs. aware timestamp columns**: the first migration generated `TIMESTAMP WITHOUT TIME ZONE` columns (SQLAlchemy's plain `DateTime` default) for `posted_at`/`ingested_at`/`created_at`, but the domain models use `datetime.now(UTC)` (timezone-aware) throughout. asyncpg rejected binding an aware datetime into a naive column (`can't subtract offset-naive and offset-aware datetimes`). Fixed by using `DateTime(timezone=True)` in the ORM models and generating a follow-up migration. Worth remembering: any future timestamp column must use `DateTime(timezone=True)` from the start, since the project's convention is UTC-aware datetimes everywhere.
- `uv sync` alone did not install the `dev` extras (pytest, mypy, ruff, factory-boy); needed `uv sync --extra dev` before tests could run at all in this session.
- Design choice: persistence for the ingestion flow lives in `infra/db/repositories/vacancy_repository.py` (upsert-by-id), not inlined in `ingestion/pipelines/`, keeping the pipeline stages pure/I/O-free and matching the ports-and-adapters split even though `ingestion/` itself isn't `domain/`.

## Session 3 — 2026-08-15

**Completed — finished all of Phase 2:**
- Added `infra/llm/client.py`: the `LLMProvider` protocol (`Message`, `complete`, `stream`) plus `AnthropicLLMProvider`, the first concrete implementation. Structured output (`response_model`) is implemented via forced tool-use (a single tool whose `input_schema` is the Pydantic model's JSON schema, `tool_choice` pinned to it) rather than any provider-specific response-format flag — this is the stable, generally-available path for schema-constrained output on Claude models. Added `core/exceptions.py` (`LLMResponseError`) for the case where the model doesn't emit the expected tool call.
- Added `parsing/schemas.py` (`ExtractedSkill`, `ExtractedCandidateProfile` — the LLM's raw extraction shape) and `parsing/resume_parser.py` (`parse_resume`). Matching free-text skill mentions to the taxonomy is left to the LLM, but which `skill_id` values are valid is enforced deterministically afterward — any `skill_id` the model returns that isn't in the known taxonomy (passed in from Postgres via a new `skill_repository.list_skills`) is silently dropped rather than trusted. This keeps the deterministic/LLM-generated split CLAUDE.md requires, even though skill *matching* itself is inherently semantic.
- Added `infra/db/repositories/candidate_repository.py` (`create_candidate` — each parse mints a new candidate row; re-parsing isn't treated as an update to a prior profile) and `infra/vector_store/candidate_index.py` (mirrors `vacancy_index.py`, embeds into the `candidates` Qdrant collection).
- Added `api/v1/candidates.py` (`POST /api/v1/candidates`, multipart file upload) wiring parser → persistence → indexing, `api/v1/router.py`, and `src/careervector/main.py` — the FastAPI entrypoint the `Dockerfile` already referenced but that Phase 1 never actually created.
- Added 3 varied sample resumes in `tests/fixtures/resumes/` (Markdown, plain text, differently-structured Markdown) covering Backend/Data/AI role types, unit tests for `resume_parser` against a fake `LLMProvider` (taxonomy-filtering behavior in particular), and integration tests for `skill_repository`/`candidate_repository` against the real seeded Postgres from Phase 1.
- All new code passes `ruff check`, `ruff format`, and `mypy --strict`; full suite is 15 passed (13 unit + 2 integration).

**Decisions / gotchas:**
- **`ruff`'s `B008` fires on FastAPI's `Depends(...)` default-argument pattern** — that pattern is the framework's own recommended idiom, not the mutable-default-argument bug bugbear is trying to catch. Fixed by adding `[tool.ruff.lint.flake8-bugbear] extend-immutable-calls = ["fastapi.Depends", "fastapi.params.Depends"]` to `pyproject.toml`. This is the standard fix for any FastAPI codebase using ruff+bugbear — worth doing once, up front, rather than re-discovering it on every new route file.
- **Cross-loop `asyncpg` failure in the integration suite**: `infra/db/session.py`'s `engine`/`async_session_factory` are module-level singletons created once at import time. `pytest-asyncio`'s default is a fresh event loop *per test function*, so the second integration test to touch the engine got `RuntimeError: Task ... got Future ... attached to a different loop` — the connection pool's first connection was bound to test 1's loop. Fixed by setting `asyncio_default_fixture_loop_scope = "session"` and `asyncio_default_test_loop_scope = "session"` in `pyproject.toml`, so all async tests in a run share one event loop, matching the module-level engine's lifetime. If a future session adds more integration tests and sees this same "different loop" error, this is almost certainly the cause — check for a module-level async engine/connection before assuming the test itself is wrong.
- **Anthropic SDK typing**: `AsyncAnthropic.messages.create`/`.stream` expect `Iterable[MessageParam]` (a `TypedDict` from `anthropic.types`), not a bare `list[dict[str, str]]` — `mypy --strict` failed until the payload was typed as `list[MessageParam]` explicitly. Also, the `LLMProvider.stream` protocol method must be declared as a plain `def stream(...) -> AsyncIterator[str]: ...` (no `async`) — an implementation that's an async generator (has `yield` inside `async def`) returns an `AsyncIterator` directly when called, it's not a coroutine that resolves to one, so declaring the protocol method itself as `async def` is a type mismatch even though it looks more consistent with `complete`.
- Live end-to-end verification (actually POSTing a resume to the running server and watching Claude parse it) was **not done this session** — `.env` still has the placeholder `ANTHROPIC_API_KEY`, and a real key needs a funded Anthropic Console account (API billing is separate from any claude.ai subscription — this surprised the user, worth remembering if it comes up again). Everything is verified instead via a fake `LLMProvider` in unit tests and real Postgres/Qdrant in integration tests, so the parsing *logic* and persistence *logic* are both confirmed correct — only the actual Claude API round-trip is unverified.

## Session 5 — 2026-08-15

**Completed — finished all of Phase 4:**
- Added `agents/schemas.py`: the LLM-generated output types for this phase — `SkillEquivalenceNote`/`SemanticGapAssessment` (gap-analyst) and `RoadmapItem`/`RoadmapOutput` (roadmap-synthesizer, covering prioritized learning roadmap + tailored resume bullets + interview prep questions). These live in `agents/`, not `domain/`, per CLAUDE.md's deterministic/LLM-generated split.
- Added `agents/state.py`: `CopilotState`, a `TypedDict(total=False)` threaded through the graph — `resume_text`/`vacancy`/`known_skills`/`llm` as inputs, `candidate`/`gap_report`/`semantic_assessment`/`roadmap` accumulated as each node runs. Used a `TypedDict` rather than a Pydantic model for the graph's internal state (the LangGraph-idiomatic choice for partial-update node returns); the state's own contents are still Pydantic models throughout, so the "Pydantic models at every boundary" rule is satisfied everywhere data actually crosses a layer boundary.
- Added `agents/nodes/parser_node.py` (thin wrapper calling Phase 2's `parsing.resume_parser.parse_resume` directly — no duplicate parsing logic), `agents/nodes/gap_analyst_node.py` (always runs the deterministic `compute_skill_gap` first; only calls the LLM if there's an actual gap; short-circuits with a canned "already covers everything" assessment otherwise), and `agents/nodes/roadmap_synthesizer_node.py` (built the roadmap/resume-bullets/interview-questions in one structured call from candidate+vacancy+gap+assessment).
- Added `agents/prompts/gap_analyst_prompt.py` and `agents/prompts/roadmap_prompt.py` — static system prompt strings, following the same forced-tool-use structured-output pattern `resume_parser.py` already established via `LLMProvider.complete(response_model=...)`.
- **Deterministic guardrails on both LLM nodes, mirroring the taxonomy-filtering pattern from `resume_parser.py`**: `gap_analyst_node` drops any `SkillEquivalenceNote` whose `missing_skill_id` isn't actually in the deterministic gap or whose `closest_candidate_skill_id` isn't actually one of the candidate's real skills; `roadmap_synthesizer_node` drops any `RoadmapItem` whose `skill_id` isn't actually missing. The LLM's own claims about which skill ids are relevant are never trusted outright — same philosophy as Phase 2, applied twice more.
- Added `agents/graph.py`: `build_copilot_graph()`/`get_copilot_graph()` (the latter `@lru_cache`'d, matching the `get_llm_provider`/`get_reranker`/`get_embedding_model` singleton convention) compiling a linear `StateGraph(CopilotState)`: `parser -> gap_analyst -> roadmap_synthesizer -> END`.
- Added `api/v1/copilot.py`: `POST /api/v1/copilot/roadmap`, request is `{resume_text, vacancy_id}`. **Design decision**: this endpoint always re-parses the resume text through the graph's own parser node rather than accepting a `candidate_id` for an already-persisted candidate from Phase 2, and it does not persist the resulting candidate. This keeps the copilot a self-contained, stateless "paste a resume, pick a vacancy, get a full roadmap" flow, distinct from the `/candidates` upload-and-persist flow — reusing `parse_resume` as a function, not requiring a prior API call. Wired into `api/v1/router.py`.

All new code passes `ruff check`, `ruff format`, and `mypy --strict`.
